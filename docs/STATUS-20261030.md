## Physical-machine result

The Acer has not been confirmed to reach macOS Recovery or desktop. Earlier Sequoia Recovery logs ended at `EXITBS:START`; the reviewed kernel version was Darwin `24.6.0`. There is no installed macOS system on the intended external Intel SSD.

Later local attempts confirmed that revised boot arguments and a corrected replacement DSDT were used, but still ended at EXITBS. A subsequent local attempt confirmed `SetupVirtualMap=False` (`VMAP 0`) without progress. Those later raw logs are not included in this publication. The October 22 patch notes describe an earlier state of the investigation and remain unchanged as history.

No physical-machine panic has identified the cause. The QEMU processor panic in the older evidence came from an experiment with CPU-state intervention, not a captured Acer panic.

## Linux measurements

The [public summary](../evidence/linux-hardware-20261030-summary.json) was transcribed from the Ubuntu live capture, running directly on the Acer. The raw archive remains local; its name and SHA256 are supplied for provenance, not as a substitute for its contents.

- iGPU: `8086:46A6`, revision `0C`, subsystem `1025:159C`, bound to i915.
- Topology: 1 slice, 5 DSS/subslices, mask `0x1F`, 16 EU per DSS, **80 EU total**. Both i915 capability and SSEU reports agree.
- GGC: **`0x02C1`** read at offset `0x50` on both `00:00.0` and `00:02.0`. The GMS field is `0x02`; the Linux decoding gives **64 MiB configured stolen memory**. This is not a measurement of the usable remainder after all reservations.
- Internal display: Intel `eDP-1`, pipe A, DDI A / PHY A, four lanes; 1920×1080 at 165 Hz during capture, with a 60 Hz mode also listed. EDID vendor/product: BOE / `0x0ABF`.
- Linux loaded `i915/adlp_guc_70.bin` version **70.36.0**, `i915/tgl_huc.bin` **7.9.3**, and `i915/adlp_dmc.bin` **2.20**. This does not establish which firmware version a macOS port can consume.
- NVIDIA `10DE:2560` remained visible and used nouveau. Only Intel connector details were collected, so this capture does not independently verify HDMI routing.
- MADT enables 16 APIC entries with CPU UIDs 0–15. Firmware also declares 64 PRxx CPU devices; that declaration alone is not a boot-failure diagnosis.
- The later capture contains 48 firmware-table files, including DSDT and 31 SSDTs. MSDM/SLIC were excluded. Do not merge its table counts with the older 43-file report.

The collector recorded no read errors for operations it attempted. Optional files that did not exist could be skipped; this is not proof that every possible GPU register or firmware property was captured. L3 bank count and usable stolen-memory boundaries remain unmeasured.

## Local Tahoe preparation

The following preparation was completed locally; it is not a newly published or physically tested EFI release:

- Official OpenCore **1.0.8 DEBUG**, with the relevant boot binaries byte-matched to the official archive.
- Seven enabled kext entries: Lilu, VirtualSMC, RealtekRTL8111, USBToolBox, UTBDefault, VoodooPS2Controller and its keyboard plugin. UTBDefault is temporary, not a validated USB map.
- Acer-derived EC/USBX, PLUG-ALT and RTC/AWAC SSDTs. The selected PLUG-ALT entries correspond to the 16 enabled MADT UIDs; this does not prove a 64-entry variant caused EXITBS.
- No replacement DSDT, ACPI rename/drop, forced-HT Kernel/Patch entries, CpuTopologyRebuild, NootedGreen or NullMoth acceleration stack.
- CPUID EAX spoof `0x000A0655` for Darwin 25.x; `ProvideCurrentCpuInfo=True`.
- Empty GPU DeviceProperties in this baseline; no `-wegnoigpu`, iGPU-disable SSDT or GPU-disabling property. The iGPU is not intentionally blocked by this configuration.
- `ocvalidate 1.0.8`, enabled-file/dependency checks and SSDT compilation passed. These checks do not establish runtime compatibility.
- Apple Tahoe **26.7.1 / 25G241** installation files and Recovery were obtained and checked locally. Recovery's own `SystemVersion.plist` confirms that version/build.
- Kingston retains Ubuntu as its default boot choice and has a GRUB entry chaining to an isolated OpenCore bootstrap. Original Ubuntu EFI files were retained and backed up. A direct firmware launch and a GRUB chainload can produce different pre-boot memory environments.
- Follow-up on 31 October: the baseline ran on the Acer. The first attempt selected the older 1401 Recovery; the second selected the correct Kingston Tahoe Recovery, read Darwin 25.6.0 and applied the CPUID patch, but still ended at EXITBS. No Recovery UI was reached. Full offline installer media has not been created, and macOS has not been installed.

The OpenCore 1.0.9 marker seen in earlier 1401 experiments is not the version used for this official 1.0.8 baseline. Historical configuration files are not silently updated to match the new local setup.

## NootedGreen / Yoga review

Review reference: [Yoga commit 9c707857](https://github.com/willyyypatootieee/Hackintosh-LenovoYoga-IrisXe-Tahoe/tree/9c7078574eed90d658eac60f7f6a1de4f3a2bed7).

The reviewed source has an `ngreen-eu=80` parser and maps it to 10 traditional TGL subslices × 8 EU. The binary in that Git snapshot and its EFI release lacks that parser and writes a 96-EU topology. A local rebuild was produced, and disassembly confirms a dynamic topology path. It remains unsigned by Apple codesign, has not passed native kmutil validation and has not been loaded on the Acer. It is not in the boot baseline.

The Yoga reference reports 96 EU and GGC `0xFEC1`; this Acer measures 80 EU and `0x02C1`. The two reviewed TGL memory-calculation sites in the downloaded payload retain their original bytes and evaluate to 64 MiB for the Acer GGC value. Yoga's two static FE/60 MiB patches and runtime YogaGMSFix must not be applied unchanged. This is a finding about the reviewed code paths, not proof that all memory allocation or driver ABI assumptions fit the Acer.

The full graphics experiment also needs HookCase, TGL kernel components and userspace/Metal/compiler components. Replacing a single EFI kext is not the whole installation. Acer's NVIDIA power resource is under PEG1; the Yoga PEG2 SSDT is not directly reusable.

## XeGfx request

[Issue #1 in this repository](https://github.com/phmthnh/Acer-Nitro-AN515-58-OpenCore-Investigation/issues/1) asks for a possible Alder Lake tester. The initial request is only:

1. The physical Intel GPU device ID.
2. The macOS version/build and BIOS graphics mode.
3. Whether OpenCore enables or blocks the iGPU.

We can supply the physical GPU ID, Linux measurements and the baseline configuration's intent now. The macOS answer must say **no confirmed Recovery/desktop and no installed system**, rather than presenting prepared `25G241` media as an OS already running. The exact saved BIOS graphics-menu value should be confirmed separately; the capture establishes an Intel-driven internal panel with NVIDIA present, not the literal menu value.

Upstream's [README](https://github.com/watchthelight-labs/XeGfx/blob/858d89d92dcdba9f3282ca91df0d86ad1458dc8e/README.md) lists Alder Lake / Raptor Lake as untested and needing generation-specific GuC firmware. Its reported results on other GPU families do not demonstrate support for this Acer.

The optional stage-2 probe is a separate step. The pinned [CONTRIBUTING instructions](https://github.com/watchthelight-labs/XeGfx/blob/858d89d92dcdba9f3282ca91df0d86ad1458dc8e/CONTRIBUTING.md) require a running macOS environment, building/installing the kext into the auxiliary collection, a reboot, then manual `kmutil` loading and selection of stage 2. The probe stage is described as read-only, but the preparation is not a no-install operation. It has not been performed here. Do not substitute the existing Linux capture for XeGfx's macOS registry/sysctl output or proceed to stage 4 merely because stage 2 was requested.

The owner has since agreed to include staged XeGfx testing in the [active plan](EXPERIMENT-PLAN-20261030.md). Follow-up on 31 October: the [initial reply is posted](https://github.com/phmthnh/Acer-Nitro-AN515-58-OpenCore-Investigation/issues/1#issuecomment-6530954373), with no upstream response present at that check. No XeGfx installation or probe result exists yet.
